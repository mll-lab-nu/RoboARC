# roboarc-ikea (the IKEA MuJoCo images)

`ghcr.io/mll-lab-nu/roboarc-ikea:<images/ikea-mujoco/VERSION>`: MuJoCo 3.14.0 (the PyPI wheel with the EPA
horizon-overflow fix byte-patched in; CPU, float64; numpy 2.5.4, Python 3.12) and the twelve IKEA furniture scenes of
the IKEA MuJoCo tasks (`tasks/roboarc-ikea-<scene>-i00-{privileged,standard}`, generated by
`scripts/ikea_mujoco/mk_tasks.py` and `mk_standard_tasks.py`; benchmark page: `docs/benchmarks/ikea_mujoco.md` at the
repository root). Every scene is a task in both modes. The privileged tasks' agent and verifier containers run this
image; so does the physics process of the standard tasks' sidecar.

Each scene is self-contained in `/opt/ikea/scenes/<scene>/`: `scene.py` (`load()` returns the scene: `S.model`,
`S.data`, `S.step(n)` = n physics steps plus the scene's mechanism, `S.success()`), `scene.xml` with the two arms, the
scene's mechanism and success modules, `task.json`, `layout.json`, `assets/` (meshes). The image holds no task code:
the tooling (`rcb_ikea.py`) and the graders are copied by each task, and no robot demo or direct-force reference is in
it. The scenes were authored by Xiaoyu and Zhen Wu's team.

`sim/` is the standard tasks' sidecar image, `ghcr.io/mll-lab-nu/roboarc-ikea-sim:<images/ikea-mujoco/sim/VERSION>`:
this image unchanged as the physics process, plus Nyx (RoboARC's renderer) in its own venv `/opt/nyx`, the GL / EGL /
OpenGL / Vulkan loaders with the NVIDIA ICD / EGL vendor files, and the studio HDRI.

## What is in them, and how each input is pinned

| input | pin |
|---|---|
| the Python base image (Python 3.12.15, Debian 13) | by digest, `python:3.12-slim@sha256:a6e34c59…` (`Dockerfile`) |
| Debian packages: OSMesa (`libosmesa6`, the verifier's replay video) in the base; `libegl1`, `libgl1`, `libopengl0`, `libglvnd0`, `libvulkan1` in `sim/` | exact versions, from the Debian snapshot archive of 2026-10-19 (`DEBIAN_SNAPSHOT`), so their dependencies resolve to the same versions too |
| wheels of the base: mujoco 3.14.0, numpy 2.5.4, glfw, PyOpenGL, typing-extensions (what `import mujoco` and its renderer load), imageio, imageio-ffmpeg, Pillow (the replay video) | `requirements.lock`: one wheel each by sha256, `--no-deps --require-hashes` |
| wheels of the Nyx venv: gs-nyx 0.1.3, torch 2.11.0+cu128 with the CUDA 12.8 libraries it loads, numpy 2.3.5, scipy, trimesh, networkx, mujoco 3.14.0, PyOpenGL, typing-extensions, setuptools, cuda-bindings | `sim/nyx-requirements.txt`: the same, one wheel each by sha256 |
| `libmujoco.so.3.14.0` | the EPA byte patch (`source/images/roboarc/mujoco-3.14.0-epa/`) asserts the wheel's and the patched file's sha256 |
| the scenes | every file's sha256 in `scripts/ikea_mujoco/assets.json` (`stage_context.py`) |

Not in the images (unused by the tasks): mujoco's other declared dependencies (absl-py, etils, fsspec, websockets,
zipp: its viewer, studio and test code), the Nyx venv's triton, sympy, mpmath, jinja2, markupsafe, filelock, fsspec,
cuda-toolkit, cuda-pathfinder, absl-py, etils, glfw and pip, curl (the sidecar downloads nothing at run time), bytecode
caches (`PYTHONDONTWRITEBYTECODE=1`: Python compiles in memory), documentation pages of added Debian packages, apt
lists and logs. The base image keeps pip and apt for the privileged agent (its instruction allows installing packages).

## Build source

The scene code is in git, `scenes/<scene>/` here. The meshes (`scenes/<scene>/assets/`, 2,078 files, about 40 MB per
scene) are not: they are in the public Hugging Face dataset
[`RoboARC/RoboARC-ikea-assets`](https://huggingface.co/datasets/RoboARC/RoboARC-ikea-assets) (layout
`<scene>/assets/<file>`), every file pinned by its sha256 in `scripts/ikea_mujoco/assets.json` (per scene `files`; its
`repo` and `revision` name the dataset revision the pins were written from, which `fetch_image_context.sh` maps to the
public dataset's commit). Every task's `tests/runtime_binding.json` repeats its scene's pins, which the grader checks
in the verifier image (`instance_exact`) together with the initial-state hash (`instance_ok`).

What is staged per scene: `scene.py`, `scene.xml`, `task.json`, `layout.json`, `sw_cutover.json` (where present), the
scene's own Python modules (not `_*.py` scripts) and `assets/`; then `assets.json` (its `note` and `tasks`, the pins the
image carries at `/opt/ikea/assets.json`), `requirements.lock` and `bytepatch_libmujoco.py`, the EPA patch script, from
RoboARC's one copy in `source/images/roboarc/mujoco-3.14.0-epa/` (`docs/simulator/MUJOCO_EPA_PATCH.md` describes the
patch). `stage_context.py` refuses any file whose sha256 differs from the pins and any scene text that points at
upstream material (PROTOCOL Appendix H.2); the scenes' upstream provenance is kept out of the image, in
`scripts/ikea_mujoco/provenance.json`.

## Build (paths from `ikea/`)

```bash
images/ikea-mujoco/build.sh                    # meshes from the HF dataset RoboARC/RoboARC-ikea-assets (no token needed)
images/ikea-mujoco/build.sh --assets <dir>     # or a local copy of the meshes, <dir>/<scene>/assets/
images/ikea-mujoco/build.sh --out <dir>        # where the OCI archives go (default: the current directory)
scripts/ikea_mujoco/fetch_image_context.sh     # the download, check and staging step alone (needs huggingface_hub)
```

`ROBOARC_IKEA_ASSETS_SOURCE=<repo>@<revision>` downloads the meshes from another copy of the dataset. Whatever the
source, every file must have its pinned sha256.

`build.sh` stages the scene code with the meshes into `images/ikea-mujoco/context/` (`stage_context.py`, every file
checked against `scripts/ikea_mujoco/assets.json`), then builds with a throwaway BuildKit builder of a pinned version,
with no provenance or SBOM attestations and every timestamp set to SOURCE_DATE_EPOCH (`rewrite-timestamp`):

1. the base image, as the OCI archive `roboarc-ikea-<VERSION>.oci.tar`;
2. the sidecar image `sim/Dockerfile`, whose `FROM` names the base by its manifest digest: the build passes the base it
   has just built as the named context of that reference, so it never pulls it, and stops when the base's digest is
   not the pinned one (after a deliberate change of the base: pin the new digest in `sim/Dockerfile` and the new id in
   `scripts/ikea_mujoco/bindings.json`). Output: `roboarc-ikea-sim-<sim/VERSION>.oci.tar`;
3. both archives loaded into the local Docker image store under their tags (`--no-load` skips it), and the check that
   the base image's id is the one every task is bound to (`scripts/ikea_mujoco/bindings.json`).

The same checkout gives the same archives, digests and image ids on any host (two builds from fresh clones on two
occasions gave identical digests). The build needs network access to docker.io, snapshot.debian.org, pypi.org,
download.pytorch.org and dl.polyhaven.org; running needs none. Host: Linux x86_64, Docker with buildx (the
docker-container driver), about 40 GB of free disk; the base image needs no GPU, the sidecar an NVIDIA GPU with Vulkan
and EGL.

After a scene changes: `stage_context.py <tree> --pin`, rebuild, bump `VERSION`, refresh
`scripts/ikea_mujoco/bindings.json` (`python /opt/tools/rcb_ikea.py info --task <scene>` in the image, per scene), upload
the meshes as a new dataset revision and pin it, and re-render the tasks. A changed scene is a new task (PROTOCOL §2.8).

## Registry

The tasks name the images by manifest digest (`images/pins.json` at the repository root); `scripts/ikea_mujoco/bindings.json` holds the base image's id, which every privileged task's
`tests/runtime_binding.json` and every standard task's `environment/sim/runtime_binding.json` repeat. Push the two OCI
archives byte for byte, so the registry's manifest digests are the ones above and `sim/Dockerfile`'s `FROM` resolves:
`images/push_all.sh` (a skopeo copy that preserves digests and checks them after the copy; the base first; the
digests are pinned in `images/pins.json`, images/README.md). A `docker push` of the loaded images would re-compress their layers and give other manifest digests (the
image ids stay). The build context's source of record is the dataset revision in `scripts/ikea_mujoco/assets.json`.
Before RoboARC 1.0.0 the 1.0.0 images (same ids) were published as `eai-ikea-mujoco:0.3.2` and `eai-ikea-mujoco-sim:0.4.2`;
the IKEA task texts and evidence records of earlier runs keep those names.
